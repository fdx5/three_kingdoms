# 삼국지 TD (sam-td)

후한 말을 배경으로 한 웹 타워 디펜스. 현재 범위는 **레벨 6까지** 이다.

| 장         | 무대                    | 가르치는 것                          |
| ---------- | ----------------------- | ------------------------------------ |
| 제 1장     | 황건적의 난             | **성장** — 배치보다 업그레이드가 먼저 |
| 제 2장     | 동탁 토벌전 · 호뢰관 앞 | **조합** — 속성에는 답이 따로 있다   |
| 제 3장     | 관도대전 · 관도 나루    | **시간** — 웨이브를 앞당겨 돈을 번다 |
| 제 4장     | 합비 공방전 · 소요진    | **성문** — 슬롯이 모자란 자리는 성이 메운다 |
| 제 5장     | 번성 공방전 · 한수 범람 | **사거리** — 불이 막히면 포탄으로 뚫는다 |
| 제 6장     | 오장원 · 마지막 북벌    | **총력** — 앞의 다섯을 한꺼번에 묻는다 |

앞 장을 클리어해야 다음 장이 열린다. 진행도와 별 등급은 **계정**에 기록된다 —
첫 화면에서 아이디와 비밀번호를 입력하면 계정이 만들어지고, 1장을 깬 계정은
다음 접속에서 2장부터 시작한다.

## 실행

```bash
npm install
npm run dev        # http://localhost:5173  — 서버 없이 바로 논다(localStorage 저장)
```

서버(토르소 DB)까지 붙여 보려면 두 개를 같이 띄운다.

```bash
cp .env.example .env      # 토르소 URL·토큰을 채운다
npm run db:setup          # 스키마 생성 + 참조 데이터 적재 (멱등)
npm run server            # http://localhost:8787  — API + 빌드된 게임
npm run dev               # 다른 터미널. http://localhost:5173/?api=/api 로 열면 DB에 저장된다
```

## 기술 스택

- Vite + TypeScript (strict)
- Three.js — WebGPURenderer 우선, 실패 시 WebGLRenderer 폴백
- HUD는 three 안이 아니라 canvas 위 **DOM + CSS 오버레이**
- 상태관리 라이브러리 없음. 자체 EventBus + 순수 시뮬레이션
- 서버: Node 표준 `http` + `@libsql/client` (프레임워크 없음)
- DB: 토르소(libSQL/SQLite)
- Vitest

## 구조의 핵심

**시뮬레이션은 three를 모른다.** `src/sim/`, `src/core/`, `src/data/` 는 three를
import할 수 없고 ESLint가 이를 강제한다. 그래서 렌더 없이 20웨이브를 돌려
밸런스를 검증할 수 있다 (`npm run sim`).

**적은 위치를 xyz로 갖지 않는다.** 경로 누적거리 스칼라 하나만 갖고,
월드 좌표는 `Path.positionAt(distance)` 로 파생된다.

**레벨은 파일 하나다.** `src/data/levels/levelNN.ts` 에 경로·슬롯·웨이브·환경색을 쓰고
`levels/index.ts` 배열에 한 줄 넣으면 그 장이 생긴다. 타워의 `unlockedIn` 이
어느 장부터 지을 수 있는지를 정한다.

**N발은 N발로 보인다.** 시뮬은 화살 수만큼 투사체를 따로 만들지만 전부 같은 지점에서
같은 순간에 떠나므로, 뷰가 `salvoIndex` 로 출발점·포물선·출발 시점을 어긋나게 해
한 덩어리로 뭉치지 않게 한다. 벽력거처럼 발사체가 1개인 타워는 대신 레벨이 오르면
바위가 달아오르고(Lv3) 불덩이가 된다(Lv5).

**에셋이 없어도 게임이 돈다.** 모델이 없으면 프리미티브 도형, 음원이 없으면 무음이다.
`public/assets/manifest.json` 에 한 줄 추가하면 그 유닛이 즉시 GLTF로 바뀌고,
그 줄을 지우면 프리미티브로 되돌아온다.

## 타워

| 타워           | 해금   | 성격                                            |
| -------------- | ------ | ----------------------------------------------- |
| 궁노 망루      | 1장    | 화살 N발이 **서로 다른 적**을 노린다. 무리에 강하다. 레벨마다 쇠뇌가 하나씩 는다 |
| 벽력거         | 2장    | 공성 피해 + 범위. 한 발에 몰아주므로 방패병·장수에 강하다. 팔이 실제로 돌을 던진다 |
| 철질려 진지    | 2장    | 피해 0, 감속만. 다른 타워의 사거리를 시간으로 늘려준다 |
| 화공 망루      | 4장    | 화염 피해. 직격은 약하고 **지면에 남는 불**이 값을 한다. 등갑처럼 잘 타는 적에 배로 들어가고, 젖은 적에겐 거의 안 통한다 |
| 화포 진지      | 5장    | 공성 피해 + 넓은 폭발 + 불구덩이. 사거리 175~210으로 가장 길다. 비싸고 느리다. 레벨을 올리면 데크의 **포문이 한 문씩 는다**(1~5문) |

## 성벽 앞의 장수

장수(중간보스·보스)는 성문 앞에 닿으면 **2초에 한 번** 성벽을 친다. 잡몹은 16초에
한 번이다. 모든 장에 같은 규칙이고, 값은 `BALANCE.castleCombat` 한 곳에 있다.
간격이 짧아진 만큼 한 대의 세기는 8분의 1로 나눴으므로 초당 피해는 예전과 같다 —
바뀐 것은 "장수가 성문 앞에서 쉬지 않고 때린다"는 체감이다.

여포처럼 날이 옆으로 뻗은 무기를 든 장수는 찌르지 않고 **어깨와 몸통을 돌려
휘두른다**(`attackStyle: 'swing'`). 자세한 것은 [docs/ASSETS.md](docs/ASSETS.md) 참고.

## 성문 (4장부터)

성은 맞기만 하는 벽이 아니라 **여섯 단계로 자라는 마지막 타워**다.
팔 수도 옮길 수도 없는 대신, 슬롯이 없는 자리에 방어선을 하나 더 세우는 유일한 방법이다.

| 단계 | 이름       | 무엇이 되는가                                    | 비용 |
| ---: | ---------- | ------------------------------------------------ | ---: |
| 1    | 성가퀴     | 활 2발 연사                                      |    — |
| 2    | 연노 성가퀴 | 활 4발 연사, 사거리 증가                        | 300 G |
| 3    | 포문       | **대포 2발** — 지면 강타 시 폭발 + 주변 지속 화염 | 520 G |
| 4    | 중포문     | 대포 2발 (폭발 반경·화염 지속 증가)              | 780 G |
| 5    | 연환포대   | **대포 4발** — 지면 지속 피해가 확연히 크다      | 1,100 G |
| 6    | 화룡구     | **좌우 망루에서 양방향 화염** — 닿으면 크게 무너진다 | 1,500 G |

단계가 오를 때마다 최대 체력도 늘고, 늘어난 만큼 즉시 채워진다.
단계별 수치는 `src/data/castle.ts` 한 파일에 있고 `tests/castle.test.ts` 가 사양대로인지 검사한다.

## 계정

첫 화면에서 아이디와 비밀번호를 받는다. 가입 화면과 로그인 화면을 나누지 않는다 —
처음 보는 아이디면 그 자리에서 계정이 만들어지고, 이미 있는 아이디는 비밀번호가 맞아야 들어간다.
같은 아이디로 두 계정을 만들 수는 없다.

진행도(어느 장까지 깼는가)·전적·방명록이 전부 계정에 붙는다. 저장소는 갈아 끼울 수 있다:

| 저장소 | 언제                       | 구현                              |
| ------ | -------------------------- | --------------------------------- |
| 브라우저 | 기본값 (서버 없이 논다)   | `src/account/LocalGameStore.ts`   |
| 토르소 DB | `?api=/api` 또는 `VITE_API_BASE` | `src/account/TorsoGameStore.ts` → `server/index.ts` |

게임 코드는 어느 쪽인지 모르고 `GameStore` 인터페이스만 본다.

**비밀번호가 오가는 방식** — PBKDF2-SHA256(12만 회, 계정마다 다른 소금)으로
브라우저에서 해시를 만들고, **비교는 저장소가 한다**(`verifyPassword`).
토르소 저장소에서는 그 비교가 서버에서 일어나고 저장된 해시는 어떤 응답에도 실리지 않는다 —
해시를 그대로 내려 주면 아이디만 알아도 오프라인에서 사전 공격을 할 수 있기 때문이다.
소금은 비밀이 아니라 그대로 내려간다(브라우저가 PBKDF2를 돌려야 한다).

아직 남은 것: 로그인 뒤에 세션 토큰을 받지 않아서, 전적·진행도 **쓰기**를 서버가
"정말 그 사람인지" 확인하지 못한다. 공개 랭킹을 열 때 손봐야 할 자리다.

## 서버와 데이터베이스

프로세스 하나가 두 가지를 한다 — `/api/*` 는 토르소를 읽고 쓰는 REST API,
그 밖의 경로는 `dist/` 의 정적 파일. 같은 오리진이라 CORS도 배포도 하나로 끝난다.

### 스키마 (`db/schema.sql`)

| 테이블 | 무엇 | 설계 이유 |
| ------ | ---- | --------- |
| `accounts` | 계정 | `password_hash` 는 서버 밖으로 안 나간다 |
| `progress` | 계정 × 레벨 별 등급 | JSON 덩어리가 아니라 **행**으로 쪼갠다 — "3장을 3별로 깬 사람 수"를 물을 수 있어야 한다 |
| `records` | 한 판의 결과 (이기든 지든) | `level_title` 을 같이 박아 둔다. 나중에 제목을 바꿔도 그때 기록은 그때 이름으로 남는다 |
| `guestbook` | 방명록 | |
| `levels` · `units` · `towers` | 게임 데이터의 사본 | 전적만으로는 "무엇에게 뚫렸는지"를 해석할 수 없다. DB가 등갑병이 화살을 65% 튕긴다는 걸 알아야 랭킹·통계를 SQL로 짤 수 있다 |

시각은 전부 **정수 밀리초(Unix epoch)** 다 — 게임이 `Date.now()` 를 쓰기 때문이다.
`v_level_best`(레벨별 최고 기록)와 `v_account_summary`(계정 요약) 두 뷰가 랭킹 질의를 맡는다.

참조 데이터는 `npm run db:seed` 가 `src/data/*` 에서 읽어 통째로 다시 채운다(멱등).
게임 데이터를 고쳤으면 다시 돌리면 DB가 코드를 따라온다.

### API

`src/account/TorsoGameStore.ts` 가 기대하는 그대로다.

| 메서드 | 경로 | 무엇 |
| ------ | ---- | ---- |
| GET | `/api/health` | 살아 있는지 + 적재된 레벨 수 |
| POST | `/api/accounts` | 가입 (201 / 409 중복) |
| GET | `/api/accounts/:id` | 계정 (해시는 빈 문자열) |
| PATCH | `/api/accounts/:id` | `lastLoginAt` · `displayName` 만 |
| POST | `/api/sessions` | `{id, passwordHash}` → 200 / 401 |
| GET · PUT | `/api/accounts/:id/progress` | 별 등급. PUT은 **더 높은 값만** 남긴다 |
| POST · GET | `/api/records` | 전적 |
| POST · GET | `/api/guestbook` | 방명록 |
| GET | `/api/leaderboard` | `?levelId=` 면 그 장의 최고 기록, 없으면 계정 요약 |
| GET | `/api/catalog` | 레벨·유닛·타워 참조 데이터 |

### 접속 정보

`.env` 에만 있고 저장소에는 없다(`.env.example` 이 그 자리를 대신한다).

| 변수 | 무엇 |
| ---- | ---- |
| `TURSO_DATABASE_URL` | `libsql://…` (또는 `file:local.db` 로 로컬 테스트) |
| `TURSO_AUTH_TOKEN` | rw 토큰 |
| `PORT` | 서버 포트 (기본 8787, render.com 은 직접 주입) |
| `VITE_API_BASE` | 클라이언트가 붙을 API. 비우면 localStorage, 배포 빌드에서는 `/api` |

### 배포 (render.com)

`render.yaml` 이 블루프린트다. New > Blueprint 로 이 저장소를 고르면 그대로 만들어진다.
Web Service 를 손으로 만들었다면 Settings 에 같은 값을 넣는다.

| 설정 | 값 |
| ---- | -- |
| Runtime | Node |
| Build Command | `npm ci && VITE_API_BASE=/api npm run build` |
| Start Command | `npm start` |
| Health Check Path | `/api/health` |
| Environment | `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`, `NODE_VERSION=22` |

**빌드에 필요한 것은 `dependencies` 에 있다.** Render 는 Node 서비스에
`NODE_ENV=production` 을 기본으로 넣고, 그러면 npm 이 devDependencies 를 건너뛴다.
그래서 빌드·기동에 실제로 필요한 넷(`vite` · `tsx` · `three` · `@libsql/client`)만
`dependencies` 에 두었다. 나머지(typescript · vitest · eslint · 에셋 파이프라인)는
전부 `devDependencies` 다 — 배포 서버에서 돌 일이 없다.

실측: `NODE_ENV=production npm ci` 로 **22개**가 깔리고 빌드가 끝난다.
`npm 설정(.npmrc)에 기대지 않는다` — 플랫폼이 `NPM_CONFIG_PRODUCTION` 같은 환경변수를
넣으면 프로젝트 `.npmrc` 보다 우선해서, 그 방법은 실제로 통하지 않았다.

**`vite.config.ts` 는 vite 만 import 한다.** 예전에는 `vitest/config` 에서
`defineConfig` 를 가져왔는데, 그러면 게임을 빌드하는 데 테스트 러너까지 필요해진다.
테스트 설정은 `vitest.config.ts` 로 나눠 두었다.

**`npm run build` 는 `vite build` 하나다.** 타입 검사를 여기 묶어 두면 배포가 그것 때문에
멈춘다 — 게다가 devDependencies 가 없는 채로 `tsc` 를 부르면 전역의 다른 버전이 잡혀
`TS5102: baseUrl has been removed` 같은 엉뚱한 오류가 난다(실제로 그랬다).
타입 검사는 `npm run typecheck` 로 로컬에서 돌린다.

접속 정보를 아직 안 넣었어도 **서버는 뜬다.** 정적 파일은 계속 서빙되고 API 는 503 과
함께 무엇이 없는지 말해 준다 — `/api/health` 를 열어 보면 한 줄로 나온다.
(헬스체크는 실패하므로 배포는 "unhealthy" 로 남는다. 환경변수를 넣고 다시 배포하면 된다.)

배포 주소: **https://three-kingdoms-cmus.onrender.com**

#### 배포가 한 시간째 "진행 중"이면 — 빌드가 안 끝나는 것이다

`npm run build` 는 **반드시 끝나야 한다.** 한때 `postbuild` 훅이 빌드 뒤에
`npm start` 를 띄웠다 — Start Command 가 빌드로 잘못 잡혀 있어도 서비스가 살게
하려는 안전장치였는데, 대가로 빌드 단계가 영영 끝나지 않았다. render.com 은 그
배포를 "진행 중"으로 붙들고, 뒤따르는 푸시는 전부 그 뒤에 줄을 선다. 로그에는
서버가 정상 기동했다고 찍혀 있어서 어디가 막혔는지도 안 보인다.

**하루치 커밋이 그렇게 배포되지 않았다.** 지금은 그 훅을 뺐고
`tests/deployConfig.test.ts` 가 다시 들어오는 것을 막는다. 대신 Start Command 가
틀렸다면 "Application exited early" 로 **빠르게** 실패한다 — 한 시간짜리 침묵보다 낫다.
대시보드 Settings > Start Command 는 `npm start` 여야 한다.

#### 배포가 됐는지 확인하는 법

```
npm run deploy:check          지금 살아 있는 커밋과 로컬 HEAD 를 비교한다
npm run deploy:check -- --wait  바뀔 때까지 기다린다
```

`/api/health` 가 `commit` 을 알려 준다(`RENDER_GIT_COMMIT`). **이게 없어서 한나절을
헤맸다** — 푸시는 됐는데 화면이 안 바뀌면 원인이 셋인데(배포가 안 걸림 / 빌드 실패 /
브라우저 캐시) 밖에서는 구분할 방법이 없었다. 사이트는 200 을 주고 있었고 다만 하루 전
빌드였을 뿐이라, 에셋 파일을 하나씩 받아 크기를 재 보고서야 알았다.

푸시하면 `.github/workflows/deploy.yml` 이 두 가지를 한다.
1. **Deploy Hook 을 직접 두드린다** — Render 의 GitHub 웹훅이 끊겨 있거나 Auto-Deploy 가
   꺼져 있어도 배포가 걸린다. Render > Settings > Deploy Hook 의 URL 을 저장소 시크릿
   `RENDER_DEPLOY_HOOK` 에 넣어야 켜진다.
2. 그 커밋이 실제로 뜰 때까지 기다리고, 안 뜨면 **워크플로가 실패한다.** 그게 알림이다.

배포가 안 걸릴 때 대시보드에서 볼 곳은 순서대로 **Events**(배포 시도 자체가 있었나 /
빌드가 실패했나), **Settings > Auto-Deploy**(On 인가), **Settings > Branch**(main 인가).
손으로 만든 Web Service 는 `render.yaml` 을 **읽지 않는다** — 그 경우 Build/Start 명령을
Settings 에 직접 넣어야 한다.

#### 15분마다 서버가 죽는 것처럼 보일 때 — 스핀다운

무료 플랜은 **15분 동안 들어오는 요청이 없으면 인스턴스를 재운다.** 크래시가 아니라
재우는 것이라 로그에 오류가 안 남고, 다음 사람이 들어오면 콜드 스타트(30초~1분)
동안 게임이 안 열린다. 두 겹으로 막는다.

| 무엇 | 어디 | 하는 일 |
| ---- | ---- | ------- |
| 자가 두드림 | `server/keepalive.ts` | 10분마다 자기 공개 주소의 `/api/health` 를 부른다. 시각이 정확하다 |
| 바깥 두드림 | `.github/workflows/keepalive.yml` | 10분마다 GitHub Actions 가 부른다. **잠든 것을 깨울 수 있다** |

둘 다 두는 이유는 서로를 못 메우기 때문이다. 이미 잠든 인스턴스는 타이머도 멈춰서
스스로 못 깬다 — 배포 교체로 틈이 한 번 생기면 자가 두드림만으로는 영영 자고 있다.
반대로 GitHub 예약 실행은 붐빌 때 10~30분씩 밀려서 15분 창을 놓친다.

끄고 싶으면 Render 대시보드에 `KEEPALIVE=off`. 간격은 `KEEPALIVE_MINUTES`(분, 15 미만).
주소는 `RENDER_EXTERNAL_URL` 을 Render 가 자동으로 넣어 주므로 따로 설정할 것이 없다.

**750시간 주의.** 무료 플랜은 계정 전체에서 월 750 인스턴스시간이다. 쉬지 않고 켜 두면
31일 달이 744시간이라 **웹 서비스 하나면 겨우 들어간다.** 무료 서비스를 하나 더 올리면
월말에 둘 다 멈춘다. 그때는 `KEEPALIVE=off` 로 끄거나 유료 플랜($7/월)으로 옮긴다 —
유료는 스핀다운도 시간 제한도 없어서 이 장치가 통째로 필요 없어진다.

GitHub 는 저장소에 60일 동안 커밋이 없으면 예약 실행을 자동으로 끈다. 그때는 Actions
탭에서 다시 켜야 한다. 검사에 실패하면 GitHub 가 메일을 보낸다 — 그게 가동 감시다.

## 계략 (2장)

남는 골드를 쓰는 일회성 카드. 타워를 대신하지는 못하고 거들기만 한다.
3장에서는 열리지 않는다 — 골드가 모자란 장에 소비처를 더 두면 함정이 되기 때문이다.

| 계략 | 비용 | 효과                                   |
| ---- | ---: | -------------------------------------- |
| 매복 | 260 G | 모든 적을 4초간 크게 늦춘다           |
| 화공 | 400 G | 모든 적에게 공성 피해 (저항 무시)     |
| 원군 | 450 G | 10초간 모든 타워의 피해량 +50%        |

## 저장소에 없는 것

`img/` 의 **원본 3D 모델은 커밋하지 않는다** (하나에 60~90MB, 전부 1.2GB).
게임에 들어가는 것은 굽고 난 결과물인 `public/assets/models/*.glb` 이고 그건 커밋한다.
원본을 다시 굽고 싶으면 `img/` 에 원본을 놓고 `npm run asset:all` 을 돌린다 —
어떤 파일이 어떤 결과물이 되는지는 `scripts/bake-assets.ts` 의 레시피에 적혀 있다.

## 밸런스 요약

**1장** — 업그레이드를 하면 배치가 나빠도 이기고, 안 하면 중간보스가 나오는
10웨이브에서 반드시 진다. 1장이 가르치는 것은 정확히 하나 — **업그레이드**다.

화살 N발은 **서로 다른 적**을 노린다. 한 마리에 몰아 쏘면 HP 20 보병에게 화살이
낭비되어 업그레이드가 체감되지 않기 때문이다. 이게 이 게임 밸런스의 중심 규칙이다.

**2장** — 성 체력이 600으로 낮아지고 누수가 실제 위협이 된다. 슬롯 6개를 전부
궁노로 채우면 방패병(원거리 저항 72%)에 막혀 **20파에서 진다**. 벽력거와 철질려를
섞어야 이기고, 남는 골드는 성벽 수리와 계략이 가져간다. 2장이 가르치는 것은
**속성에는 답이 따로 있다**는 것이다.

계략은 승패를 뒤집지 않는다 — 잘못된 배치는 계략을 아무리 써도 진다. 대신
장수가 나왔을 때 아껴 썼는지가 등급을 가른다(안 씀 48% / 헤프게 65% / 아껴서 85%).

**3장** — 이번에는 골드가 모자란다. 처치 골드만으로는 권장 조합(7,000 G)을 완성할 수
없고, 부족분은 **웨이브를 앞당겨** 메워야 한다. 당긴 웨이브는 앞 웨이브와 겹쳐 오므로
공짜가 아니다. 조기 소집을 쓰면 이기고 안 쓰면 **9파에서 무너진다**.
하북 기수는 주변 아군을 1.45배로 가속시켜, 끊지 않으면 웨이브 전체가 앞당겨 도착한다 —
플레이어가 스스로 조기 소집을 당한 셈이 된다.

**4장** — 슬롯이 다섯뿐이고 가장 좋은 자리도 278u밖에 못 덮는다(3장의 최고 자리는 409u).
타워만으로는 성 앞 직선을 막을 수 없어서, 모자란 한 겹을 **성문 강화**로 사야 한다
(실측: 같은 타워로도 성문을 안 올리면 진다). 등갑병은 화살을 65% 튕기고 불에는 2.2배로
타므로 궁노 도배는 6파에서 무너진다.

**5장** — 관우의 수공으로 적이 전부 젖어 있어 4장에서 배운 화공이 통하지 않는다(화염 저항 80%).
슬롯 하나는 사거리 100으로는 경로에 닿지도 못하고 사거리 175면 511u를 덮는다 —
"사거리가 곧 성능"인 자리다. 답은 **화포 진지**다. 성문은 여기서 필수가 아니지만
안 올리면 성 체력이 3분의 1로 끝난다(998 -> 266).

**6장** — 앞의 다섯이 한꺼번에 온다. 슬롯 여덟을 전부 만렙으로 올려도 성문을 안 올리면
14파에서 진다 — 목우유마가 성문 앞에 모이면 서로를 회복시켜 1단계 성문으로는 영영 못 죽인다.
제갈량은 저항 두 겹에 회복·가속 오라를 동시에 두르므로 먼저 끊는 것 말고는 답이 없다.
